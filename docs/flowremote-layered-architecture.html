The stack

L1 Presentation - mobile app phone, 8 screens

Show the authoritative state, collect the operator's intent, and expose exactly two human gates. No business rule is decided here.

Login and saved account Home and device status Task setup (source, batch, targets) Validation progress Awaiting review: tally, filter, exception cards Decision controls: Accept / Edit / Skip Execution approval summary Execution progress Results and activity log App bar with notification badge
  • Renders what the server reports; a disabled control mirrors a guard, it does not enforce it.
  • Proceed to Approval stays disabled while unresolved > 0.
↓Operator intent: start validation, Accept / Edit / Skip, proceed, approve
↑Rendered snapshot, review tally, progress, activity events
L2 Client application - phone runtime no authority

Keep the last known state, queue intent while the network is unreliable, and reconcile on reconnect.

Session store (work email, token, role) Task snapshot cache Event stream client with resumable cursor Optimistic decision queue Progress subscriptions Gate notifications
  • On state_conflict the client drops local guesses and re-renders from the server snapshot.
  • A queued decision or approval must survive a dropped connection (INV-12).
↓Command with idempotency key: decisionId, approvalId, attempt, stateVersion
↑State feed: state.changed with counters, proceedEnabled, reasonCode
L3 Interface - the contract one boundary, versioned

Every layer boundary is one contract: commands are idempotent, queries are cheap, events are resumable.

startValidation recordDecision(accept|edit|skip) reopenDecision proceedToApproval approveAndExecute retryExecution cancelTask taskSnapshot exceptions?filter= validationProgress executionProgress activityLog?cursor= stream state.changed
  • Guard names match the state machine spec: unresolved = 0, approvedCount > 0, approval not yet recorded.
  • Guards are evaluated server-side. The client may only mirror the outcome.
↓Validated command, stateVersion checked before it is applied
↑Authoritative state, counters, proceedEnabled, reason codes
Gate 1 - reviewProceed to Approval is released only when unresolved = 0.
Gate 2 - approvalapproveAndExecute is the only event that releases a write to OA or BI.
L4 Control plane - backend services state authority

Own the task state machine, the review tally, the approval, and the audit trail. Everything else reports to this layer.

Task orchestrator (transitions T1-T19) Review tally service Approval service (single use per attempt) Exception service (per record, per field) Dispatch and queue to the device agent Activity log (append only) Telemetry and analytics
  • Tally invariant: accepted + manual + skipped + unresolved = exceptionCount at every moment (INV-6).
  • State chain in the storyboard: 100 input, 88 passed, 12 exceptions, 8 accepted, 3 manual, 1 skipped, 99 ready.
  • Every state change appends one activity event with actor or engine and timestamp (BR-10).
↓Dispatch: startValidation, then targetActions(approved set) with one action per target
↓no dispatch before an approval is recorded (BR-2, INV-2)
↑Progress, heartbeat, per-target outcome, failure reason codes
L5 Automation runtime - device side Office-PC-01, Online

Do the mechanical work where the source and the target systems are actually reachable.

Device agent (registration, dispatch intake, heartbeat) FlowRemote Engine - validation RPA Execution Engine - write and sync Target connectors: OA, BI Progress and event reporter
  • Validation is read-only: it never updates OA or BI (BR-1).
  • The write set is the approved set: 99 written and synced, 1 skipped excluded (BR-3).
  • The demo's 3 s auto-advance lives in a simulated runtime, not in the product.
↓Read the source batch; request a suggestion per flagged field
↑Suggestion value, confidence, reason
↩Source records and the workflow template are read by L5 and L4 respectively
L6 Intelligence and data services shared services

Supply what the run needs to be possible: the batch to read, a template to follow, and the advice a human reviews.

AI suggestion service (customer registry, order history) Confidence thresholds and rationale text Company Workspace - source workbook Workflow template store (predefined workflow)
  • A suggestion is advice, never a decision: 98% unique match, 84% no reliable suggestion, 68% below threshold in the storyboard.
  • Read by L4 (template, batch definition, thresholds) and by L5 (source file, suggestions).
↓After approval only: write 99 records to OA (primary), then sync the same 99 to BI (secondary)
↑Per-target outcome: accepted, rejected, partial
↓the same record ids to both targets, never a second copy (BR-5, INV-5)
L7 Systems of record - external owned by other teams

Hold the truth about orders and reporting. FlowRemote writes into them; it does not own them.

OA - Order Administration (primary target) BI - Business Intelligence (secondary target)
  • OA and BI receive the same record set, not 198 records for 99 inputs.
  • The phone has no network path to either system; only the device side writes.

Cross-cutting concerns

Identity and session (work email sign-in) Authorization: who may approve Audit: append-only activity log Notifications: gate reached, bell badge Observability: heartbeat, stale detection, reason codes Configuration: workflow template, target set, thresholds Idempotency: decision, approval, attempt
  • These are used by every layer, so they are owned by L4 and consumed, never re-implemented, by the rest.

Build order this diagram implies

  1. Freeze L3 first. Commands, queries, the state feed payload, and the idempotency keys. Every other layer is developed against it, and it is the only boundary that both sides must agree on.
  2. Implement L4 as pure logic. The state machine, the tally, and the two gates, covered by tests derived from INV-1 to INV-14. This layer can run before any device exists.
  3. Stub L5 behind the same contract. A simulated device agent that emits progress and completion lets L1 and L2 be built and demoed with the storyboard's numbers.
  4. Add L6 and L7 last. Suggestion quality and real target connectors only change behaviour inside L5; they must not change L1 to L4.
Storyboard chain carried by these layers: 100 input → 88 passed + 12 exceptions → 8 accepted + 3 manual + 1 skipped → 99 approved → OA write 99 and BI sync 99 → 99/100 in 42.8 s, 99.0%

Not shown in this diagram, by design of the storyboard: failure and recovery paths (ValidationFailed, ExecutionPartial, retry and reconciliation), multi-device routing, and workflow authoring. See the state machine specification for the recommended states and the PRD for the open questions (Q1-Q12).

  • Evidence: storyboard screens 1-11 and the 4 board annotations (Proceed gated on unresolved = 0; no write before approval; OA and BI get the same 99; timed auto-transitions in the demo).
